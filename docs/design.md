# poh-backlog-skills — дизайн

**Дата:** 2026-08-18
**Статус:** согласован, готов к плану реализации
**Репозиторий:** `po-helper-org/poh-backlog-skills`

---

## 1. Проблема

Product Owner тратит время на вычитку и нормализацию беклога: хвосты, кривые
связи, пустые описания, протухшие приоритеты, дубли. Работа рутинная,
воспроизводимая и не требует продуктового суждения в большинстве случаев — но
съедает часы и делается нерегулярно.

Масштаб измерен на реальной выборке 727 задач проектов ARM, KIONCMS, MGW,
MEDIAWEB, MP001 (`mts-ai-hub/agents/rate/jira-statistics.md`):

| Дефект | Доля задач |
|---|---|
| Нет описания | ~27% |
| Нет компонентов (команды) | ~80% |
| Нет labels | ~60% |
| Менее 20 слов в описании | ~40% |

Существующие наработки покрывают задачу частично и разрозненно: `poh-issue-agents`
реагирует на одиночный Issue, `mts-ai-hub` содержит роли PM без метода
декомпозиции и без записи решений обратно в трекер.

## 2. Миссия

Агент, поддерживающий гигиену и чистоту беклога. Снимает с PO необходимость
вычитывать беклог вручную. Работает независимо от трекера: ценность в наборе
принципов и правил принятия решений, не в интеграции с конкретным API.

Функции целевого состояния:

1. Разбор эпика на набор отдельных историй
2. Сбор операционных метрик команды
3. Заведение багов, историй, подзадач
4. Заполнение описаний
5. Актуализация приоритетов
6. Комментарии о проделанной работе
7. Разделение истории на сутевую часть и техдолг-хвост
8. Линковка задач с правильными эпиками (эпик-инициатива, эпик-фича)

Каркасом для направлений 1, 7 и 8 служит модель фаз фичи (раздел 5): истории
раскладываются по MVP / Grow / Support, «сутевая часть против техдолг-хвоста»
становится «MVP против Grow», а правильность линковки — проверяемым инвариантом.

Первый срез даёт диагностику и план действий по направлениям 4, 5, 7, 8, плюс
дубли, протухшее и нераздробленные эпики как находки. Направление 1 (генерация
историй) приходит срезом 4, направление 2 (метрики) — срезом 5. Направления 3 и 6
реализуются как операции плана, исполняемые host-агентом.

## 3. Опора на рынок

Решение не изобретается с нуля. Заимствованные практики и их источники:

| Практика | Что берём | Источник |
|---|---|---|
| Разделение агентов | Узкие агенты (organizer, planner, readiness checker) вместо одного толстого | Atlassian Rovo, out-of-the-box агенты |
| Формат выхода | Sprint planning brief: health-метрики, shortlist, список решений PO, дифф с прошлого прогона | Gravity |
| Корзины действий | Close / Merge / Update / Split / Link / No-Action | Cotera, кейс 847 → 312 тикетов |
| Дубли | Семантическое сравнение, не keyword | Linear Agent |
| Декомпозиция | SPIDR: Spike, Path, Interface, Data, Rules | Mike Cohn |
| Критерий элемента | INVEST + acceptance criteria до оценки | Definition of Ready |
| Критерий беклога | DEEP: detailed, emergent, estimated, prioritized | Scrum-практика |
| Пороги здоровья | <20% элементов старше 90 дней, <5% старше 180 | Backlog health benchmarks |
| Метрики команды | Flow metrics (cycle time, WIP, WIP age, throughput) + DORA | Закон Литтла |
| Техдолг | Ноль теневого учёта: каждый хвост — тикет с label, severity, effort, impact; 15–20% ёмкости спринта | Age-of-Product, Atlassian |
| Иерархия | Инициатива → эпик → история; отчёт orphan issues | Advanced Roadmaps / Plans |

Общий паттерн всех работающих решений: **агент курирует, человек решает.**
Cotera: ревью 847 тикетов человеком заняло ~4 часа против недель ручного
грумминга. Ограничения тоже общие — агент не оценивает стратегический приоритет
и ошибается на намеренно расплывчатых ideation-тикетах.

## 4. Архитектура

### 4.1 Границы

`poh-backlog-skills` решает и помнит. Он не ходит в трекер.

| Роль | Владеет | Кто |
|---|---|---|
| Решающий слой | правила, вердикты, план, память, диффы | `poh-backlog-skills` |
| Руки | доступы, чтение беклога, исполнение плана | host-агент (Claude Code / Codex / `poh-issue-agents`) |
| Судья | суждения там, где детерминизм не работает | host-модель либо `LLM_BASE_URL` |

Следствия: в репозитории нет секретов и сетевых зависимостей; детерминированная
часть тестируется офлайн на фикстурах; смена трекера не трогает правила.

### 4.2 Разграничение с poh-issue-agents

`poh-issue-agents` — **реактивный, по одному Issue**: webhook, intake-gate,
4-way классификация, приоритет по формуле, duplicate-check.

`poh-backlog-skills` — **периодический, по всему беклогу**: аудит, дифф, план.

Функционального пересечения нет. Общее — знание: `poh-issue-agents` импортирует
`rules/` и заменяет ими собственные `config/priority-weights.toml` и
`config/estimation-rules.toml`.

### 4.3 Раскладка

```
poh-backlog-skills/
├─ VISION.md · README.md · install.sh          # конвенция poh-org
├─ backlog-profile.template.yaml               # домен: пороги, типы, иерархия, маппинг
├─ rules/                                      # rules-as-data, единственный источник истины
│  ├─ catalog.yaml        # HYG-STALE-001 ... : id, severity, корзина, вход, порог, источник
│  ├─ thresholds.yaml     # дефолты с обоснованием
│  ├─ dor.yaml            # Definition of Ready как чек-лист
│  ├─ hierarchy.yaml      # инициатива → эпик → история; что считать сиротой
│  └─ split.yaml          # оси SPIDR + правило «суть / техдолг-хвост»
├─ schemas/               # backlog-item · finding · plan · state (JSON Schema)
├─ mappings/              # github.yaml · jira.yaml — поля трекера → каноническая модель
├─ prompts/               # суждения: duplicate_cluster · priority_mismatch · split_story
├─ poh_backlog/           # тонкий Python
│  ├─ rules/              # чистые функции, детерминированные проверки
│  ├─ judge.py            # два режима: harness | api
│  ├─ diff.py · planner.py · memory.py · cli.py
├─ skills/ · commands/    # обёртки для Claude Code / Codex
└─ tests/fixtures/        # conformance-кейс на каждый rule_id
```

`rules/` — данные, а не код: любой потребитель на любом языке читает те же YAML.

### 4.4 Раннер

Один пайплайн, одни промпт-шаблоны, два режима суждения:

- **harness** — запущен внутри Claude Code / Codex; суждения делает host-модель,
  оплачено подпиской, доступны инструменты хоста.
- **api** — OpenAI-совместимый вызов по `LLM_BASE_URL` / `LLM_API_KEY`.

Детерминированная часть в обоих режимах одна и та же и не зависит от модели.

## 5. Модель фаз фичи

Каркас, вокруг которого строится вся гигиена. Три фазы жизни функциональности:

| Фаза | Что это | Где живёт | Чем заканчивается |
|---|---|---|---|
| **MVP** | закрывает ключевую проблему; есть бизнес-метрика, срок, HowToDemo, явный список ограничений; edge-кейсов нет | тег `mvp` на истории внутри эпика фичи | HowToDemo проходит |
| **Grow** | доводит MVP до прода: edge-кейсы, расширения, снятие ограничений | тег `grow` в том же эпике | прод-релиз |
| **Support** | бесконечные расширения после прода: баги, запросы | отдельный Support-эпик | не заканчивается |

Структура в трекере:

```
Бизнес-инициатива
├─ Эпик фичи A          # конечный, точные границы и сроки
│  ├─ история [mvp]
│  ├─ история [mvp]
│  └─ история [grow]
├─ Эпик фичи B
└─ Support-эпик         # один на инициативу, растёт и сжигается, не закрывается
```

Границей и сроком владеет эпик фичи. MVP и Grow различаются тегом внутри него.
Support — принадлежность к Support-эпику инициативы.

Следствие для агента: фаза выражена тегом, а не связью, поэтому её легко
переставить незаметно. Дрейф фаз не виден в одном снимке — он ловится диффом
между прогонами (раздел 6).

### 5.1 Инварианты

| ID | Инвариант | Вид |
|---|---|---|
| `PHS-TAG-001` | История в эпике фичи несёт ровно один тег фазы | детерминированное |
| `PHS-EPIC-002` | Эпик фичи имеет бизнес-метрику, срок, HowToDemo и список ограничений | детерминированное |
| `PHS-MVP-003` | MVP-история необходима для прохождения HowToDemo | суждение |
| `PHS-LIMIT-004` | Каждое ограничение MVP имеет Grow-историю либо пометку «принято навсегда» | суждение |
| `PHS-GROW-005` | Эпик фичи не закрывается, пока есть открытые Grow-истории без явного переноса или отмены | детерминированное |
| `PHS-SUP-006` | Задача после прод-релиза, по сути поддержка, живёт в Support-эпике, а не в эпике фичи | суждение |
| `PHS-SUP-007` | Support-эпик существует ровно один на бизнес-инициативу и не закрывается | детерминированное |
| `PHS-DRIFT-008` | Перевод истории `grow` → `mvp` после фиксации границ требует обоснования в комментарии | детерминированное, работает на диффе |

`PHS-MVP-003` — главное правило модели. HowToDemo превращает принадлежность к MVP
из вкусовщины в проверяемое утверждение: если демо проходит без этой истории,
история не MVP. Оно же питает расщепление (функция 7 раздела 2) — история,
наполовину нужная для демо, режется на MVP-часть и Grow-хвост.

`PHS-LIMIT-004` закрывает главную протечку: ограничения MVP, не обращённые в
Grow-истории, — это техдолг, которого нет ни в одном списке.

### 5.2 Метрики фаз

- **Чистота MVP** — доля MVP-историй, необходимых для HowToDemo
- **Дрейф границ** — рост story points по тегу `mvp` после фиксации эпика
- **Покрытие хвостов** — доля ограничений MVP, имеющих Grow-историю или явное принятие
- **Утечка Support** — доля задач поддержки, висящих в эпиках фич
- **Лид-тайм MVP → прод** — длительность фазы Grow
- **Баланс Support-эпика** — приток против сжигания

Баланс Support считается отдельно от прочего: этот эпик не закрывается, поэтому
его размер сам по себе ничего не означает. Значение имеет производная —
устойчивый приток выше сжигания говорит, что фича не стабилизировалась.

## 6. Поток данных

Единица обмена между репозиторием и host — файл, не вызов. Поэтому цикл
одинаково работает под Claude Code, Codex и голым API.

| Шаг демо | Кто исполняет | Артефакт |
|---|---|---|
| 1. Доступы настроены | host | вне репозитория |
| 2. Пробуждение по расписанию | cron / CI / `poh-scheduller` | вызов `poh-backlog run` |
| 3. Аудит беклога | host читает беклог по `mappings/` → `items.json`; репозиторий считает | `findings.json` |
| 4. Отчёт об изменениях с прошлого запуска | `diff.py` против прошлого `state/<run-id>/` | `report.md` |
| 5. Набор ключевых действий | `planner.py`: findings → корзины | `plan.md` + `plan.json` |
| 6. Человек+агент правят план | человек снимает галочки в `plan.md`, коммитит | утверждённый `plan.md` |
| 7. Исполнение | host исполняет утверждённое своими инструментами | записи в трекере |
| 8. Проверка исполнения и аудит | повторный аудит + сверка «действие → ожидаемый эффект» | `verify.md` |
| 9. Фиксация состояния | `snapshot` → новый `state/<run-id>/` + задача в Backlog.md | память |
| 10. Выборочная проверка | человек | — |

Шаг 6 — жёсткий гейт. Без утверждённого `plan.md` шаг 7 не стартует.
Неотмеченное действие не исполняется.

## 7. Память

Два слоя, по конвенции `poh-core/backlog-ops.template.md`: штаб хранит указатель
и статус, содержимое живёт в артефакте.

### 7.1 Backlog.md — операционный штаб

Инструмент: https://github.com/MrLesk/Backlog.md

Один прогон аудита = одна задача, label `hygiene`. Acceptance Criteria — стадии
пайплайна:

```
audit · diff · plan · approve · apply · verify · snapshot
```

Отмеченный AC показывает, на чём цикл оборвался. Описание задачи — указатель на
`state/<run-id>/`, без дублирования содержимого. Доску можно потерять: она
пересобирается из `state/`.

### 7.2 state/ — артефакт под git

```
state/<run-id>/
├─ items.snapshot.json    # id, updated_at, хэш значимых полей
├─ findings.json
├─ plan.json
└─ applied.json           # выполненные action_key
```

### 7.3 decisions.yaml — подавления

Отклонённое человеком не должно возвращаться каждый прогон:

```yaml
- rule_id: HYG-STALE-001
  item: GH-412
  verdict: rejected
  reason: "релиз отложен, задача живая"
  suppress_until: 2026-12-01     # либо forever
```

Без этого слоя агент через месяц становится шумом и его перестают читать. Это
самый частый провал подобных агентов.

## 8. Каталог правил и профиль

### 8.1 Формат записи

```yaml
- id: HYG-STALE-001
  title: Задача без активности дольше порога
  bucket: close                      # close | merge | update | split | link | no-action
  kind: deterministic                # deterministic | judgment
  severity: medium
  inputs: [updated_at, status, links]
  threshold: profile.staleness.story_days
  rationale: "Возраст без активности и без связанной работы = кандидат на закрытие"
  source: "backlog health: <20% элементов >90 дней, <5% >180"
  action: propose_close              # комментарий + метка, никогда не удаление
  expected_effect: "item.labels contains 'stale' and item has comment with rule_id"
  maturity: experimental             # experimental | advisory | trusted
  quality:                           # последний замер, пишется `poh-backlog eval`
    precision: null
    recall: null
    acceptance_rate: null
```

Правила-суждения вместо `threshold` ссылаются на промпт:
`prompt: prompts/duplicate_cluster.md`.

`rule_id` устойчив и сквозной: попадает в finding, в план, в комментарий трекера
и в снимок состояния. Даёт трассировку «почему агент это предложил».

### 8.2 Разрешение порогов

Три слоя, каждый следующий переопределяет предыдущий:

```
rules/thresholds.yaml  →  backlog-profile.yaml  →  флаг CLI
```

Профиль валидируется JSON-схемой. Неизвестный ключ — ошибка, не молчание.
Профиль также указывает используемый маппинг и кастомные поля трекера
(например, Jira Epic Link `customfield_10101`).

## 9. Ошибки, идемпотентность, безопасность

- **Ничего деструктивного.** `close` — это метка плюс комментарий с `rule_id`.
  Операции удаления в словаре нет вообще.
- **Идемпотентность.** `action_key = hash(rule_id + item_id + item_revision)`.
  Ключ пишется в `applied.json`; повтор — no-op. Прогон плана дважды даёт ноль
  изменений.
- **Нет данных — есть находка.** Отсутствующее поле даёт finding «оценка
  невозможна», а не тихое исключение элемента из аудита.
- **Явный потолок.** `max_actions_per_run` в профиле; отложенное перечисляется в
  `plan.md` открытым списком. Молчаливое усечение запрещено — оно читается как
  «покрыли всё».
- **Суждения не автоприменяются.** У judgment-находки есть `confidence`, галочку
  ставит человек. Автоапрув требует одновременно трёх условий: правило
  детерминированное, `maturity: trusted` (раздел 11.1) и явное включение в белый
  список профиля.
- **Секреты.** `LLM_API_KEY` только из переменных окружения, никогда в `state/` и
  `plan.*`. Репозиторий не хранит доступов к трекерам.

## 10. Тестирование

- **Conformance на каждый `rule_id`**: фикстура беклога плюс ожидаемый набор
  findings. Изменение порога без обновления кейса даёт красный тест.
- **Судья стабится** в юнит-тестах. Для промптов — отдельный небольшой
  golden-набор с ручной разметкой, гоняется по требованию, не в CI.
- **Дифф**: два снимка → ожидаемый отчёт об изменениях.
- **Идемпотентность**: применить план дважды, второй раз ноль операций.
- **Профиль**: битый YAML и неизвестный ключ падают с внятной ошибкой.
- Порог покрытия фиксирует текущий уровень, как `.coveragerc` в
  `poh-issue-agents`.

## 11. Контроль качества

Под «качеством» скрыты три разных вопроса, и мерить их надо по-разному:

| Вопрос | Провал выглядит так | Инструмент |
|---|---|---|
| **Верность** | правило считает не то, что заявлено | conformance-тесты, раздел 10 |
| **Меткость** | агент предлагает не то, что решил бы PO | golden set, acceptance rate |
| **Полезность** | беклог не чище, PO не экономит время | outcome-метрики против baseline |

### 11.1 Зрелость правила как гейт

Поле `maturity` в каталоге определяет, что правилу разрешено:

| Уровень | Разрешено | Условие перехода |
|---|---|---|
| `experimental` | только `report.md`; в план не попадает | стартовое состояние нового правила |
| `advisory` | попадает в план, всегда ручная галочка | precision ≥ порога корзины на golden set |
| `trusted` | допускается в белый список автоприменения | precision ≥ порога **и** acceptance rate ≥ 0.8 на ≥ 5 прогонах |

Продвижение только по измеренным данным. Новое правило физически не может ничего
натворить в первый день. Откат автоматический: падение acceptance rate ниже
порога возвращает правило с `trusted` на `advisory`.

### 11.2 Асимметричные приёмочные пороги

Ошибки не равноценны: ложное «закрыть живую задачу» дороже пропущенного мусора.
`eval/thresholds.yaml`:

| Корзина | Precision | Recall | Логика |
|---|---|---|---|
| close, merge | ≥ 0.90 | ≥ 0.50 | врать нельзя, пропускать можно |
| split, link | ≥ 0.75 | ≥ 0.70 | обратимо |
| update | ≥ 0.60 | ≥ 0.80 | дешёвая ошибка, важна полнота |

### 11.3 Shadow-режим — источник эталона

Golden set не размечается заранее. Первые прогоны идут с флагом `--shadow`:
цикл отрабатывает целиком до шага 6, человек проставляет галочки как обычно, но
шаг 7 отключён — ничего не исполняется. Проставленные и снятые галочки
записываются в `eval/golden/` как эталонные вердикты.

Выход из shadow — по правилу, не по прогону: как только правило набрало
достаточно размеченных случаев и прошло пороги, оно переходит в `advisory` и
начинает исполняться.

Цена: первые цифры появляются через несколько недель. Взамен — ноль предоплаты
временем PO и разметка на реальных, а не отобранных случаях.

### 11.4 Живые метрики

- **Acceptance rate** — доля предложенных действий, утверждённых человеком, в
  разрезе `rule_id` и прогона. Тренд — главный индикатор деградации.
- **Suppression rate** — доля находок правила, ушедших в `decisions.yaml` как
  `rejected`. Выше 30% означает кривой порог; правило выключается.
- **Execution fidelity** — доля действий с подтверждённым `expected_effect`.
  Меньше 1.0 означает, что host-агент отчитался об исполнении, которого не было.
  Это то, что человек ловит выборочно на шаге 10, а метрика ловит сплошняком.
- **Noise ratio** — находок на 100 элементов беклога. Резкий рост после смены
  профиля или модели — сигнал регресса.

### 11.5 Полезность

Замеряется до первого прогона и складывается в `eval/baseline.json`:

- Backlog Health — доля элементов, проходящих DoR
- доля элементов старше 90 и 180 дней
- доля сирот без родителя
- время PO на грумминг, самозамер
- **застой** — доля находок, повторяющихся из прогона в прогон без движения

Застой — единственная метрика, где рост однозначно плох: агента читают, но не
слушают. Провал, маскирующийся под работу.

### 11.6 Ловушки

`eval/traps/` — случаи, на которых подобные агенты ломаются стабильно:

- намеренно расплывчатые ideation-тикеты — трогать нельзя
- старые, но живые: ждут внешней зависимости
- похожий текст, разный контекст — не дубли
- эпики-контейнеры, выглядящие брошенными
- активность только в связанных PR, не в трекере

Прогоняются при каждой смене промпта или модели. Судья недетерминирован, поэтому
проверяется и стабильность: один вход дважды даёт один вердикт.

### 11.7 Раскладка

```
eval/
├─ golden/           # размеченные срезы: items + эталонные вердикты
├─ traps/            # ловушки
├─ thresholds.yaml   # приёмочные пороги по корзинам
└─ baseline.json     # состояние до внедрения
```

Команда `poh-backlog eval` считает метрики, пишет `eval-report.md` и обновляет
блок `quality` в `rules/catalog.yaml`.

| # | Срез | Содержание |

| **1** | **Аудит и память** | rules-as-data, детерминированные проверки включая `PHS-*`, дифф, `plan.md`, Backlog.md-штаб, `decisions.yaml`. Маппинг GitHub, режим harness. Прогоны в `--shadow`: план формируется и размечается, исполнения нет |

## 13. Принятые решения

| Решение | Выбор | Причина |
|---|---|---|
| Форма знания | Rules-as-data плюс skills поверх | Один источник истины для человека и сервиса; исключает расхождение методологии между трекерами |
| Граница | Решающий слой плюс маппинги полей, ноль сетевого I/O | Нет секретов, офлайн-тесты, не дублирует `poh-issue-agents` |
| Первый срез | Аудит гигиены | Read-only, безопасно прогнать по реальному беклогу сразу; валидировано рынком |
| Домен | Дефолты плюс `backlog-profile.yaml` | Конвенция `domain-profile.template.md` из `poh-core` и `poh-sprint-agents` |
| Движок | Гибрид: код для детерминированного, промпты для суждений | Тестируемость плюс семантические дубли; `poh-issue-agents` на Python импортирует напрямую |
| Dogfood | GitHub Issues через `poh-issue-agents` | Сервис уже боевой, есть DRY_RUN и тесты — петля обратной связи замыкается быстрее |
| Исполнение | Host-агент пишет в трекер, репозиторий владеет памятью | Сохраняет «ноль I/O», переиспользует уже настроенные доступы |
| Апрув | Файл плана с галочками под git | Работает асинхронно и с телефона, вся история в git |
| Раннер | Один раннер, режимы harness и api | Одна оркестрация, не расходится; подписка используется бесплатно |
| Упаковка | Python-пакет с CLI; каталог правил с устойчивыми ID и conformance-кейсы | Дешёвая часть подхода «спека плюс реализация» без стоимости мультиязычной спеки |
| Гейт качества | Зрелость правила: experimental → advisory → trusted, продвижение по измеренным порогам | Новое правило не может навредить в первый день; откат автоматический по acceptance rate |
| Эталон | Shadow-режим, разметка копится из живых апрувов | Ноль предоплаты временем PO, разметка на реальных случаях, а не на отобранных |
| Модель фаз | Эпик фичи владеет границей и сроком; MVP и Grow — теги внутри него; Support — один вечный эпик на бизнес-инициативу | Соответствует реальному процессу PO; даёт HowToDemo как проверяемый критерий принадлежности к MVP |
