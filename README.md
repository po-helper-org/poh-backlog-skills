# poh-backlog-skills

Решающий слой гигиены беклога. Решает и помнит; в трекер не ходит.

## Что делает

Читает нормализованный `items.json`, прогоняет детерминированные правила из
`poh_backlog/data/catalog.yaml`, выдаёт находки, отчёт об изменениях с прошлого прогона
и план действий с галочками. Исполняет план host-агент своими инструментами:
пакет не вызывает ни Backlog.md, ни какой-либо трекер напрямую.

## Границы

- Ноль сетевых вызовов. Нет клиентов Jira и GitHub, нет секретов
- Ничего деструктивного: операции удаления в словаре допустимых действий нет
  (`propose_close`, `propose_merge`, `update_field`, `relink`, `split`, `comment`)
- Правила-суждения (`PHS-MVP-003`, `PHS-LIMIT-004`, `PHS-SUP-006`) пропускаются:
  они требуют модели и приходят отдельным подпроектом. `run` печатает, сколько
  правил пропущено и какие именно
- Маппинг источника — только GitHub (`poh_backlog/data/mappings/github.yaml`). Его читает
  host-агент при сборке `items.json`; сам пакет этот файл не исполняет.
  Jira-маппинг — отдельный подпроект
- Нет команды `eval` и метрик меткости по прогонам: `verify` считает
  достоверность исполнения только за один прогон, накопление — другой
  подпроект
- Нет автоприменения ни для одного правила: всё, что войдёт в план, исполняет
  host-агент только по утверждённой человеком галочке. Пакет план предлагает
  и проверяет, но сам ничего не меняет и не решает

## Быстрый старт

```bash
pip install -e ".[dev]"
poh-backlog run \
  --items items.json \
  --out out \
  --state state \
  --run-id 2026-08-18-01 \
  --shadow
```

`run` пишет `out/findings.json`, `out/report.md`, `out/plan.md`, `out/plan.json`
и снимок текущего прогона в `state/<run-id>/`. Флаг `--shadow` сохраняется в
`plan.json`: прогон в этом режиме ничего не утверждает, а `approve` для его
плана впоследствии тоже не утвердит ничего, даже если кто-то вручную
проставит галочки в `plan.md` — shadow существует, чтобы копить размеченные
данные бесплатно, не давая одобрить план, который для этого не предназначен.

`run` отказывается перезаписывать `out/plan.md`, если в нём уже стоит хоть
одна отметка (галочка или явный отказ) — то есть человек уже начал с ним
работать. Он завершится кодом `2` с сообщением, что нужно сначала выполнить
`approve` либо указать другой `--out`. План, в котором не проставлено ни
одной отметки, перезаписывается свободно — это нужно для идемпотентных
повторных прогонов и cron.

У каждого действия в `plan.md` три возможных состояния, а не два:

- `- [x]` — утверждено, уйдёт в `out/approved.json`;
- `- [-]` — явно отклонено, уйдёт в `decisions.yaml` как постоянное
  подавление, чтобы не возвращаться следующим прогоном;
- `- [ ]` (нетронуто) — решения не было. Действие не исполняется и не
  подавляется, а просто снова появляется в плане следующего прогона. Молчание
  не означает отказ: план с 50 действиями, из которых отметили только 3,
  не подавляет оставшиеся 47 навсегда.

Разметить план: проставить галочки и явные отказы в `out/plan.md`, затем

```bash
poh-backlog approve --out out --decisions decisions.yaml
```

`approve` печатает все три количества (утверждено, отклонено, не решено) и
сверяет `plan.md` с `plan.json` по идентификатору прогона: если `plan.md`
оказался перезаписан другим прогоном (идентификаторы разошлись), апрув
отменяется кодом `2`, а не молча принимает чужие отметки.

Исполняет утверждённые действия host-агент своими инструментами — пакет к
трекеру не ходит. Когда исполнение сделано (или заведомо не сделано), собрать
свежий срез беклога и проверить, что случилось:

```bash
poh-backlog verify --items items-after.json --out out --state state
```

`verify` сверяет каждое действие из `out/approved.json` с этим свежим срезом
и выносит один из трёх вердиктов:

- `done` — метка `poh:<rule_id>` на месте, и находка, породившая действие,
  по свежим данным больше не подтверждается (либо для правил с меткой как
  единственным доказательством — метка и есть подтверждение);
- `no_effect` — метка стоит, но результата нет: host отчитался, эффекта не
  случилось;
- `not_applied` — метки нет вовсе, хотя человек утвердил действие, либо
  элемент вообще пропал из свежего среза.

**Контракт следа для host-агентов:** исполнив действие, обязательно
поставьте на элемент метку `poh:<rule_id>` (например, `poh:HYG-STALE-001`) —
без неё `verify` не сможет отличить неисполненное от исполненного без
эффекта. Готовое значение метки лежит в поле `trace_label` каждого действия
в `approved.json`, придумывать его вручную не нужно.

`verify` пишет `out/verify.md` (вердикты, достоверность исполнения — доля
действий с вердиктом `done` — и раздел «изменено вне плана», если снимок
«до» найден) и `state/<run-id>/verdicts.json`, а также наполняет
`state/<run-id>/applied.json` — ключами действий этого прогона, доехавших до
`done`.

`verdicts.json` — накопительный журнал, а не снимок последнего прогона:
каждый вызов `verify` переносит в него из прошлого прогона любую пару
`(rule_id, item_id)`, которую `out/approved.json` этого прогона не покрыл, —
поэтому запись выживает даже в прогоне, где `approve` вообще ничего не
утвердил. Пара уходит из журнала только тремя способами: вердикт `done`,
явный отказ `[-]` (уходит в `decisions.yaml` как подавление, см. ниже) или
истечение обычного `suppress_until`. Поэтому `verify` тоже принимает
`--decisions` — без него не от чего отличить «подавлено» от «просто
нерешено».

Действия с вердиктом `not_applied` или `no_effect` не теряются: следующий
`run` поднимает их в раздел плана «Обещано, не сделано» с указанием прогона,
где их утверждали, и с исходным обоснованием находки, к которому дописана
заметка `verify` о том, почему подтверждение не засчиталось. Утверждение не
действует вечно — такое действие приходит с пустой галочкой и требует
нового решения при следующем `approve`. Явный `[-]` на таком действии
работает так же, как на свежей находке: `approve` пишет то же самое
постоянное подавление в `decisions.yaml`, и следующий `run` больше не
поднимает эту пару — гейт подавления один на находки и на обещания.

Такие действия не считаются в `plan.max_actions_per_run`: потолок бьёт
только по свежим находкам, из которых собирается план (`build_plan`
обрезает именно их). «Обещано, не сделано» добавляется к плану уже поверх
потолка, поэтому итоговое число действий в `plan.md` может быть больше
`max_actions_per_run`. Это осознанное решение: молча уронить одобренное
человеком обещание — то самое бесследное исчезновение, от которого этот
раздел и существует, — было бы хуже, чем план чуть длиннее заявленного
потолка. Каждое такое действие в плане размечено явно, поэтому правило
проекта против молчаливого урезания не нарушается. Если та же пара снова
попадает в план как свежая находка — хоть в число действий, хоть за
потолок, в «Отложено» — побеждает обещанная копия: дедупликация по
`action_key` вычёркивает дубликат из обоих списков, чтобы план не называл
одно и то же действие одновременно утверждаемым и отложенным.

Оба варианта завершения регламентированы: `0` — успех, `2` — читаемая ошибка
одной строкой (битый снимок прошлого прогона в `state/`, битый
`decisions.yaml`, попытка `run` затереть размеченный `plan.md`,
рассинхронизированные `plan.md`/`plan.json` при `approve`, отсутствующий или
битый `plan.json`/`approved.json` при `verify`), а не сырой traceback. Такую
ошибку удобно заметить, запуская команды из cron.

### Флаги `run`

| Флаг | Обязателен | Назначение |
|---|---|---|
| `--items` | да | путь к нормализованному `items.json` |
| `--out` | да | каталог для артефактов прогона |
| `--state` | да | каталог памяти прошлых прогонов |
| `--run-id` | да | идентификатор прогона (используется в `state/<run-id>/`) |
| `--now` | нет | момент времени для аудита, по умолчанию — текущий; значение без часового пояса трактуется как UTC |
| `--profile` | нет | доменный профиль поверх дефолтных порогов |
| `--decisions` | нет | путь к `decisions.yaml`, по умолчанию `decisions.yaml` |
| `--catalog` | нет | путь к каталогу правил, по умолчанию `poh_backlog/data/catalog.yaml` |
| `--thresholds` | нет | путь к дефолтным порогам, по умолчанию `poh_backlog/data/thresholds.yaml` |
| `--shadow` | нет | ничего не утверждать: режим накопления разметки (флаг сохраняется в `plan.json`, `approve` не утвердит план такого прогона) |

### Флаги `approve`

| Флаг | Обязателен | Назначение |
|---|---|---|
| `--out` | да | каталог с артефактами прогона (`plan.md`, `plan.json`) |
| `--decisions` | нет | путь к `decisions.yaml`, по умолчанию `decisions.yaml` |

### Флаги `verify`

| Флаг | Обязателен | Назначение |
|---|---|---|
| `--items` | да | свежий срез беклога, собранный host-агентом после исполнения |
| `--out` | да | каталог с артефактами прогона (`approved.json`, `plan.json`) |
| `--state` | да | каталог памяти прошлых прогонов; run_id для проверки берётся из `plan.json` |
| `--now` | нет | момент проверки, по умолчанию — текущий; значение без часового пояса трактуется как UTC |
| `--profile` | нет | доменный профиль поверх дефолтных порогов |
| `--decisions` | нет | путь к `decisions.yaml`, по умолчанию `decisions.yaml`; нужен для переноса и подавления пар в накопительном журнале обещаний (`verdicts.json`) |
| `--catalog` | нет | путь к каталогу правил, по умолчанию `poh_backlog/data/catalog.yaml` |
| `--thresholds` | нет | путь к дефолтным порогам, по умолчанию `poh_backlog/data/thresholds.yaml` |

## Модель фаз

Эпик фичи владеет границей и сроком. `mvp` и `grow` — теги на историях внутри
него. Support — отдельный вечный эпик, один на бизнес-инициативу.
