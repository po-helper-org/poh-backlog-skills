# poh-backlog-skills

Решающий слой гигиены беклога. Решает и помнит; в трекер не ходит.

## Что делает

Читает нормализованный `items.json`, прогоняет детерминированные правила из
`poh_backlog/data/catalog.yaml`, выдаёт находки, отчёт об изменениях с прошлого прогона
и план действий с галочками. Исполняет план host-агент своими инструментами:
пакет не вызывает ни Backlog.md, ни какой-либо трекер напрямую.

## Границы среза 1

- Ноль сетевых вызовов. Нет клиентов Jira и GitHub, нет секретов
- Ничего деструктивного: операции удаления в словаре допустимых действий нет
  (`propose_close`, `propose_merge`, `update_field`, `relink`, `split`, `comment`)
- Правила-суждения (`PHS-MVP-003`, `PHS-LIMIT-004`, `PHS-SUP-006`) в этом
  срезе пропускаются: они требуют модели и приходят срезом 2. `run` печатает,
  сколько правил пропущено и какие именно
- Маппинг источника — только GitHub (`poh_backlog/data/mappings/github.yaml`). Его читает
  host-агент при сборке `items.json`; сам пакет этот файл не исполняет.
  Jira-маппинг — срез 3
- Нет команд `eval` и `verify`: сверка ожидаемого эффекта и выход правил из
  `experimental` — срез 2

## Быстрый старт

```bash
pip install -e ".[dev]"
poh-backlog run \
  --items items.json \
  --out out \
  --state state \
  --run-id 2026-08-18-01 \
  --shadow
```

`run` пишет `out/findings.json`, `out/report.md`, `out/plan.md`, `out/plan.json`
и снимок текущего прогона в `state/<run-id>/`. Флаг `--shadow` сохраняется в
`plan.json`: прогон в этом режиме ничего не утверждает, а `approve` для его
плана впоследствии тоже не утвердит ничего, даже если кто-то вручную
проставит галочки в `plan.md` — shadow существует, чтобы копить размеченные
данные бесплатно, не давая одобрить план, который для этого не предназначен.

`run` отказывается перезаписывать `out/plan.md`, если в нём уже стоит хоть
одна отметка (галочка или явный отказ) — то есть человек уже начал с ним
работать. Он завершится кодом `2` с сообщением, что нужно сначала выполнить
`approve` либо указать другой `--out`. План, в котором не проставлено ни
одной отметки, перезаписывается свободно — это нужно для идемпотентных
повторных прогонов и cron.

У каждого действия в `plan.md` три возможных состояния, а не два:

- `- [x]` — утверждено, уйдёт в `out/approved.json`;
- `- [-]` — явно отклонено, уйдёт в `decisions.yaml` как постоянное
  подавление, чтобы не возвращаться следующим прогоном;
- `- [ ]` (нетронуто) — решения не было. Действие не исполняется и не
  подавляется, а просто снова появляется в плане следующего прогона. Молчание
  не означает отказ: план с 50 действиями, из которых отметили только 3,
  не подавляет оставшиеся 47 навсегда.

Разметить план: проставить галочки и явные отказы в `out/plan.md`, затем

```bash
poh-backlog approve --out out --decisions decisions.yaml
```

`approve` печатает все три количества (утверждено, отклонено, не решено) и
сверяет `plan.md` с `plan.json` по идентификатору прогона: если `plan.md`
оказался перезаписан другим прогоном (идентификаторы разошлись), апрув
отменяется кодом `2`, а не молча принимает чужие отметки.

Оба варианта завершения регламентированы: `0` — успех, `2` — читаемая ошибка
одной строкой (битый снимок прошлого прогона в `state/`, битый
`decisions.yaml`, попытка `run` затереть размеченный `plan.md` или
рассинхронизированные `plan.md`/`plan.json` при `approve`), а не сырой
traceback. Такую ошибку удобно заметить, запуская `run` из cron.

### Флаги `run`

| Флаг | Обязателен | Назначение |
|---|---|---|
| `--items` | да | путь к нормализованному `items.json` |
| `--out` | да | каталог для артефактов прогона |
| `--state` | да | каталог памяти прошлых прогонов |
| `--run-id` | да | идентификатор прогона (используется в `state/<run-id>/`) |
| `--now` | нет | момент времени для аудита, по умолчанию — текущий; значение без часового пояса трактуется как UTC |
| `--profile` | нет | доменный профиль поверх дефолтных порогов |
| `--decisions` | нет | путь к `decisions.yaml`, по умолчанию `decisions.yaml` |
| `--catalog` | нет | путь к каталогу правил, по умолчанию `poh_backlog/data/catalog.yaml` |
| `--thresholds` | нет | путь к дефолтным порогам, по умолчанию `poh_backlog/data/thresholds.yaml` |
| `--shadow` | нет | ничего не утверждать: режим накопления разметки (флаг сохраняется в `plan.json`, `approve` не утвердит план такого прогона) |

### Флаги `approve`

| Флаг | Обязателен | Назначение |
|---|---|---|
| `--out` | да | каталог с артефактами прогона (`plan.md`, `plan.json`) |
| `--decisions` | нет | путь к `decisions.yaml`, по умолчанию `decisions.yaml` |

## Модель фаз

Эпик фичи владеет границей и сроком. `mvp` и `grow` — теги на историях внутри
него. Support — отдельный вечный эпик, один на бизнес-инициативу.
